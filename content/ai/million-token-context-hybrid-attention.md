# 百万 Token 上下文是怎么炼成的？从 KV Cache 到混合线性注意力

> 2026 年 7-8 月，Kimi K3（2.8 万亿参数）、Qwen3.8-Max（2.4 万亿）、DeepSeek V4 系列密集发布，它们有一个共同的卖点：**100 万 token 上下文窗口**——相当于一口气"读"完一整部《红楼梦》。这背后不是简单的堆算力，而是一场注意力机制的架构革命。本文带你从 KV Cache 出发，拆解百万上下文背后的四板斧。

---

## 一、先讲人话：模型"读书"为什么这么贵？

想象你让一个人复述一本书。最笨的办法：每说一个字，就把整本书从头到尾重读一遍——这就是**没有 KV Cache 的 Transformer**。

2017 年的 Transformer 论文（Attention Is All You Need）奠定了"注意力"机制：每个词都要和前面所有词做一次"关联打分"。这带来了两个数学上的硬伤：

- **计算量 O(n²)**：序列长度 n 翻一倍，计算量变 4 倍（prefill 阶段）
- **显存 O(n)**：每个新词都要记住前面所有词的 K/V 向量（decode 阶段）

所以业界发明了第一板斧。

## 二、第一板斧：KV Cache——给模型发一本"读书笔记"

KV Cache 的思路极简：**prefill 阶段通读全文、把每个词的 Key/Value 向量记进"笔记"；decode 阶段只查笔记，不再重读原文。**

```
无 KV Cache（复读机）         有 KV Cache（做笔记）
生成第 5 个词 → 重算 1-4 词    生成第 5 个词 → 只算第 5 词
生成第 6 个词 → 重算 1-5 词    生成第 6 个词 → 只算第 6 词
... 总计算量 O(n²)            ... 总计算量 O(n)
```

但笔记本身也占地方。算一笔账：一个 7B 模型（GQA，8 个 KV 头，维度 128，32 层，FP16）：

```text
每 token 每层：2 × 8 × 128 × 2 字节 = 4 KB
100 万 token：4 KB × 32 层 × 1M ≈ 128 GB
```

一张 A100（80GB）都装不下！**上下文越长，KV Cache 越肥**——这正是"百万上下文"最大的拦路虎。

## 三、第二板斧：MLA——把笔记写成摘要

DeepSeek 在 2024 年的 V2 中给出了优雅答案：**MLA（Multi-head Latent Attention，多头潜在注意力）**。

思路：与其把每个头的 K/V 原样存下来，不如先把它们压缩进一个低维"潜空间"，用的时候再解压。

```
MHA：存全部 KV ────────────► 显存占用 1x
MLA：存低维潜向量 ──────────► 显存占用 ≈ 1/15（减少 93%）
```

代价是什么？多了一次压缩/解压的矩阵运算。但在推理场景，**显存带宽远比算力稀缺**，这笔买卖非常划算——MLA 因此成为 DeepSeek V2/V3 的招牌，也启发了 Kimi K2 等一批模型。

到了 2026 年的 DeepSeek V4，KV Cache 被进一步压到极致：官方称 100 万上下文下，**KV Cache 只有 GQA-bf16 基线模型的约 2%**。

## 四、第三板斧：线性注意力——换一种记忆方式

MLA 是"把笔记写得更薄"，但笔记还是会随长度增长。有没有可能**根本不记笔记**？

这就是线性注意力 / 状态空间模型（SSM）的路线：把"外部笔记"换成"脑内记忆"——用一个**固定大小的状态向量**滚动更新，读完全文只占用恒定内存。

- 2023 年：Mamba 横空出世，用"选择性扫描"让状态只记住重要信息
- 2024 年：Mamba-2（结构化状态空间）、Gated DeltaNet（可学习的"遗忘门"，用 delta 规则更新记忆）
- 2026 年：**KDA（Kimi Delta Attention）**——月之暗面在 Gated DeltaNet 基础上加了**通道级细粒度门控**，每个维度独立决定"记多少、忘多少"，记忆控制更精细

月之暗面 2026 年初发布的 Kimi Linear 技术报告给出了硬数据：**KDA 与 MLA 按 3:1 比例混合，KV Cache 最多减少 75%，100 万上下文下解码吞吐提升最高 6.3 倍**。

但天下没有免费的午餐：线性注意力的"记忆"是固定容量的，**在检索、复制等需要精确定位的任务上明显弱于全注意力**——就像人脑记不住电话号码，必须查通讯录。所以，纯线性路线一直没能取代 Transformer。

## 五、第四板斧：稀疏注意力——选择性阅读

既然"每词都看全篇"太贵，那就**跳读**：

- **滑动窗口**（Mistral，2023）：只关注最近 N 个词——"刚说过的记得，早说过的忘了"
- **DeepSeek Sparse Attention**（V3.2，2025）：先识别"重点词"（heavy hitter，类似文章的标题句），只让它们参与全局注意力
- **DeepSeek V4**：把 Compressed Sparse（压缩稀疏）、Heavily Compressed（重度压缩）、Sliding Window（滑动窗口）三类注意力层交错堆叠，各司其职

## 六、汇流：混合架构 = 2026 年的主流答案

把四板斧组合起来，就是当下所有旗舰模型的共同选择：

| 模型 | 总参数 | 激活参数 | 注意力架构 | 上下文 | 开源 |
|---|---|---|---|---|---|
| Kimi K3（月之暗面，7/16） | 2.8T | 104B | KDA 线性 + MLA 混合、Attention Residuals | 1M | ✅ 7/27 已开源 |
| Qwen3.8-Max（阿里，8/3） | 2.4T | ~95B | 混合注意力（MoE） | 1M | 承诺 8 月中旬开源 |
| DeepSeek V4-Pro（4/24） | 1.6T | 49B | 混合压缩注意力（稀疏×3 种交错） | 1M | ✅ MIT |

**混合架构的逻辑**：大部分层用线性注意力（省 KV Cache、高吞吐），少数层保留全注意力（保证检索质量）——"能用脑记的用脑记，记不住的查笔记"。

Kimi K3 还叠加了两项配套创新：

1. **Stable LatentMoE**：896 个专家只激活 16 个，配合 KDA 让扩展效率比 K2 提升约 2.5 倍
2. **Attention Residuals（注意力残差）**：跨层"高速通道"，让深层模型的信息传递不衰减——2.8 万亿参数的模型训练更稳

工程侧同样在跟进：Kimi 开源的 FlashKDA 内核在 H20 上预填充速度提升 1.72~2.22 倍，MoonEP 解决专家并行负载均衡；vLLM 等推理框架把 KV Cache 管理（分页、量化、分层卸载）做成了基础设施。Kimi K3 也在 Frontend Code Arena 以 1679 Elo 登顶，成为**首个在编码榜单超过闭源模型的开源模型**——长上下文 + 高效架构的组合正在兑现为真实能力。

## 七、总结：从"算得快"到"记得住"，再到"读得懂"

回头看这四板斧，其实对应着四种工程智慧：

| 板斧 | 代表技术 | 解决什么 |
|---|---|---|
| KV Cache | 推理框架标配 | 避免重复计算 |
| MLA | DeepSeek V2/V3 | 压缩 KV 显存 |
| 线性注意力 | Mamba / KDA | 恒定内存的"脑内记忆" |
| 稀疏注意力 | DSA / 滑动窗口 | 选择性阅读 |

注意力是 Transformer 的灵魂，但 2026 年的答案是：**别让注意力干所有活**。对开发者而言，百万上下文意味着 Agent 可以带着整个代码仓库、整月对话历史连续工作；而选型时也请记住：**别只看总参数，要看激活参数和 KV Cache 占用**——那才是长上下文场景下真正的成本。
