# 你的 Agent 每一步都在重复付钱：KV Cache 命中率与前缀缓存的内核原理

> 2026 年，"上下文工程"（Context Engineering）已经从小众话题变成 AI 工程的显学：Anthropic 发布了 Agent 上下文管理指南，Redis 发布了《State of Context Engineering》行业调研，各大厂纷纷把上下文当作"一级基础设施"来治理。而在这股热潮的最前面，Manus 团队留下过一句被反复引用的话：
>
> **"如果只能选一个指标，KV Cache 命中率是生产阶段 AI Agent 最重要的单一指标，它直接影响延迟和成本。"**
>
> 为什么是缓存命中率，而不是参数量、benchmark 分数？因为这句话暴露了一个真相：**Agent 的账单，大头不在"思考"，而在"重新读题"**。这篇文章带你从推理引擎的内核层面看懂这件事。

## 一、先讲人话：一位没有短期记忆的学霸

把 LLM 想象成一位**每次被叫到名字就彻底失忆的学霸**：

- 你给他一本 500 页的书，问一个问题。他会从第 1 页开始，一页一页认真读完，读到最后一页时才开口回答；
- 你追问第二个问题，他**又从第 1 页读起**——刚才读过的一页都没记住；
- 唯一的补救：允许他把阅读过程中的"读书笔记"（KV Cache）留在桌上。同一个问题继续追问时，翻笔记就行，不用重读原书。

但笔记有两个致命限制：**桌子（显存）有限**，而且**人一走（请求结束）笔记就作废**。Transformer 的自回归机制决定了：想生成第 1000 个 token，模型需要前 999 个 token 的 Key/Value 向量。没有缓存，就是每生成一个词都从头重算——这就是 prefill（预填充）阶段 O(n²) 的由来。

而 Agent 恰恰是"把同一本书反复读几十遍"的重度受害者。

## 二、Agent 的上下文长什么样：一座冰山 + 一根针

一次普通对话，上下文里历史占一半。但 Agent 完全不同。它的每一步大致长这样：

```
┌─────────────────────────────────────────────┐
│ 工具定义(tools)  系统提示  RAG材料  历史步骤… │ ← 每次请求都一模一样（冰山）
├─────────────────────────────────────────────┤
│ 上一步的工具返回 + 本步要做的决策              │ ← 真正新增的只有这一小条（针）
└─────────────────────────────────────────────┘
```

一个挂了 20 个工具、跑了 30 步的编码 Agent，第 31 步的 prompt 可能有 120K token 是**和上一步逐字节相同的前缀**，新增内容只有几百 token。生产环境的 Agent 负载里，输入:输出 token 比常见 10:1，极端能到 100:1——也就是说，**你付的钱 99% 花在"输入"上，而其中 95% 以上是在重复计算同一段前缀**。

如果推理引擎能认出"这段前缀我几秒前刚算过"，直接复用缓存好的 KV 矩阵，那么：

- **TTFT（首 token 延迟）** 从"重算 120K token"变成"只算几百个新 token"，快一个数量级；
- **成本**：云厂商把这个复用直接写进了价目表——Anthropic 的缓存读只收基础输入价的 **0.1×**（写缓存 1.25×），OpenAI 对命中前缀给 **50% 起** 的折扣（新模型最高到 90%）。

这就是"命中率 = 最重要的单一指标"的算术根据。同样一个 Agent，命中率 90% 和命中率 10%，账单和体感速度差的是**十倍**，而且 benchmark 上完全看不出来——因为跑分测的是单轮对话，Agent 死于多轮。

## 三、为什么只能复用"前缀"？——因果注意力的铁律

直觉上最方便的缓存应该是"哪段算过算哪段"，为什么所有引擎都死守"前缀"？这要回到 Transformer 的一个本质属性：**causal attention（因果注意力）下，每个 token 的 K/V 向量依赖它前面的所有 token**。

改一个字符，等价于从那个位置起，后面所有 token 的 K/V 全部作废：

```
prompt A: [系统提示X][工具集T][历史H1]        → 算出 KV(a1…a120k)，可缓存
prompt B: [系统提示X'][工具集T][历史H1]       → X 变了 1 个 token
                ↑
          从第 5 个 token 起，后面 12 万个 KV 全部对不上
```

所以前缀缓存的准确说法是：**只要动了前缀里的任意一个 token，缓存就"雪崩"**。这听起来很脆弱，但它带来一个极其好用的性质——前缀相同 ⇔ KV 相同，于是我们可以给"前缀"算指纹，用指纹做缓存 key。

如果你眼熟这套逻辑：**内容寻址（content-addressable）+ 链式哈希**——没错，这就是 git commit 和区块链的同款思想。vLLM v1 的实现里，KV Cache 按固定块（通常 16 token 一块）切分，每块的哈希把**父块哈希**卷进来：

```python
# vLLM 式块哈希链（伪代码）
hash(block_0) = sha256(GENESIS,       tokens[0:16])
hash(block_1) = sha256(hash(block_0), tokens[16:32])
hash(block_2) = sha256(hash(block_1), tokens[32:48])
# 命中 block_5 的哈希 ⇒ 0~4 块必然逐 token 相同，一次查表验证整个前缀
```

一个哈希命中 = 整段前缀有效。这就是"链式哈希把 O(n) 的前缀比较压缩成 O(1) 查表"。

## 四、两种内核：vLLM 的哈希表 vs SGLang 的基数树

两大开源推理引擎对同一问题给出了风格迥异的解，正好是两种经典数据结构的对照实验：

| | **vLLM（Automatic Prefix Caching）** | **SGLang（RadixAttention）** |
|---|---|---|
| 数据结构 | 全局哈希表 `hash → 物理块` | 基数树（压缩前缀树），节点持块引用 |
| 匹配粒度 | 块对齐（16 token 一跳） | token 级最长前缀匹配 |
| 跨请求共享 | 同哈希的物理块引用计数 ++ | 树上多条路径指向同一批物理块 |
| 淘汰策略 | 引用计数为 0 的块按 LRU 淘汰 | LRU 剪引用为 0 的叶子节点，向根蔓延 |
| 血统 | OS 页缓存（page cache） | 路由表 / Linux 内核 radix tree |

值得展开一句 SGLang 的**基数树（radix tree）**：它是 Trie 的压缩版——边的标签不是单个字符而是"一段 token"，只有真正发生分叉才新建节点。多个用户共用同一个系统提示、同一份工具定义时，它们在树顶共享同一条"主干道"，各自的历史在下游分叉：

```
                [系统提示 + 工具集]        ← 所有请求共享的主干（缓存一次，处处命中）
                 /          \
          [用户甲的历史]   [用户乙的历史]
              /    \            \
       [步32输入] [压缩摘要]   [步9输入]     ← 分叉点之后才是各自的 KV
```

节点引用计数归零不立即释放——树本身成了"最近用过的公共前缀"的索引，淘汰时从最冷叶子往上剪，天然近似 LRU。这套结构在 2024 年随 SGLang 论文拿了 NeurIPS 奖项，如今已是各引擎的标配思路。

再往深看一层，会发现 vLLM 早期 RFC 里自己就点破了天机：**"把 KV block 当作操作系统里的普通缓存来管理"**——内容寻址、引用计数、LRU 逐出、块设备分页（PagedAttention 灵感直接来自虚存页表）。一个 Transformer 推理缓存，把操作系统页缓存和数据库 Buffer Pool 几十年前的内核设计三件套原样复刻了一遍。**这不是巧合，是所有"贵资源 + 重复访问"系统的必然收敛解。**

## 五、工程守则：把上下文"设计成可命中的"

内核再聪明，也救不了乱写 prompt 的 Agent 框架。前缀缓存反过来定义了上下文工程的几条硬规矩：

1. **只追加，不修改（append-only）**。任何时候重写、删除、"整理"历史消息 = 亲手清空全部缓存。Claude Code / Manus 们不约而同把 Agent 循环写成纯追加的消息流，一半原因是这个。
2. **稳定在前，易变在后**。按"几乎不变 → 每步都变"排布：工具定义 → 系统提示 → RAG 材料 → 对话历史 → 最新观测。往 prompt 开头塞一个时间戳，等于给整棵缓存树放火。（注意 Anthropic 的缓存处理顺序恰好是 **tools → system → messages**，写反了会静默失效。）
3. **压缩要挑时机**。LLM 摘要式压缩（summarization）必然引发缓存全灭，所以它该是"撞墙才用"的兜底动作——只在接近窗口上限时执行一次，而不是每步都瘦身。
4. **别让缓存跟着实例漂移**。多副本部署时，同一会话的请求随机打到不同机器，每台各算各的 KV，命中率归零。解法是**前缀感知路由**（llm-d、各大厂推理网关的做法）：按最长前缀匹配把请求调度到已持有该 KV 的实例——数据库"分片路由"的又一次轮回。
5. **把命中率当一等指标监控**。API 侧看 `cache_read_input_tokens / input_tokens`；自建引擎看前缀命中率与 TTFT 分位数。不监控命中率的 Agent 团队，等于在盲付"重复计算税"。

## 六、尾声：上下文窗口是新的内存，命中率是新的分页算法

回头看，2026 年 Agent 工程的"新瓶装旧酒"清单长得惊人：

- **KV Cache** ≈ CPU 的一级缓存：容量小、极贵、命中即免费；
- **上下文窗口** ≈ 内存：装不下的分页（offload）到磁盘；
- **外部记忆/文件系统（CLAUDE.md、scratchpad）** ≈ 磁盘：慢但近乎无限；
- **Write / Select / Compress / Isolate 四大策略** ≈ 操作系统管理内存的那套老功夫：换页、缓存、压缩、隔离进程地址空间。

所以 Manus 那句话真正的含义不是"优化一个参数"，而是一种架构观：**LLM 是无状态的纯函数，Agent 的全部"智能连续性"都活在上下文里；上下文即内存，内存即成本**。模型每进步一代，窗口更大、单价更低，但只要 Agent 还是"多步循环调用同一个无状态函数"，前缀复用就永远是第一性问题。

下次当你发现自己的 Agent "每一步都比上一步慢、账单比产出涨得快"，先别急着换模型——大概率不是它变笨了，而是你某处一个小小的"改写了历史"，让那位失忆学霸又开始从头读书了。
