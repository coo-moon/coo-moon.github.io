## 引子：一副挽具的重量

Harness 的本义是**挽具**——套在马身上、把马力接到车上的那套皮带和金属件。它不产生一匹马力。但没有它，马再强壮，也只能在原地尥蹶子。

2026 年，AI 工程师重新捡起了这个词。

2026 年上半年，Martin Fowler 与 Addy Osmani 先后撰文讨论 Harness Engineering；Anthropic 公开了长时运行 Agent 的 harness 设计；OpenAI 的 Codex 团队则用这套方法产出了上百万行代码（据其公开复盘）。8 月 12 日深夜，DeepSeek 上线 V4 Pro；十几个小时后，又把 DeepSeek Harness 以 MIT 协议开源，官网首页只写了一行公式：

```text {linenos=false}
Agent = Model + Harness
```

一个模型公司，同一天交出一副大脑和一具身体。这个动作本身就是 2026 年的注脚：**模型决定你能做什么，harness 决定你能不能稳定地做成。**

## 一、定义：模型之外，皆是 Harness

Harness 是所有不属于模型本身的代码、配置与执行逻辑：主循环、工具执行、上下文管理、状态持久化、沙箱、审批、日志、UI。实践者 Viv Trivedy 把它压缩成上面那行公式，随后被整个行业引用。

它和常见的"Agent 框架"不是一回事：

| 层 | 回答的问题 | 代表 | 给你的东西 |
|---|---|---|---|
| Framework | 怎么拼 | LangChain、LangGraph | 积木，不替你决定怎么搭 |
| **Harness** | 怎么可靠地跑 | Claude Code、Codex、DeepSeek Harness | 有主张的运行时：默认的上下文管理、隔离、审批、回滚 |
| Agent | 做什么 | 你的业务逻辑 | 目标、策略、领域提示词 |

```text {linenos=false}
┌──────────────────────────────────────────────┐
│  Agent（做什么）：目标 · 策略 · 领域提示词        │
├──────────────────────────────────────────────┤
│  Harness（怎么可靠地做）                        │
│  循环控制 · 上下文预算 · 工具执行 · 沙箱          │
│  审批门 · 状态持久化 · 可观测性 · 回放            │
├──────────────────────────────────────────────┤
│  Model（用什么做）：权重 · 推理 · 生成            │
└──────────────────────────────────────────────┘
```

一个裸模型不是 Agent。harness 给它状态、工具、反馈和约束之后，它才变成 Agent。

## 二、为什么是 2026：错误会复利

两年里，Agent 的任务从"补全一段代码"变成"独立跑完一个两小时的项目"。变化的不只是时长。

假设单步成功率 99%，100 步串联的整体成功率是 0.99 的 100 次方，约 36.6%。每一步都"几乎没错"，整体却只有三分之一能交付。即便单步提升到 99.9%，100 步后也只剩 90.5%。**错误不是线性累加，而是复利。**

模型越强，单步成功率越高；但任务的地平线也在同步变长。能力增长和错误累积在赛跑。Harness 的第一职责，从来不是让模型不犯错，而是让错误变得**可发现、可回滚、可重试**——把一次性的赌博，变成可管理的工程过程。

这也是为什么 2026 年的模型公司都在做 harness：当权重层面的边际收益递减，可靠性就成了新的战场。

## 三、Harness 的内核：一次操作系统的完整重演

1964 年，IBM System/360 把"指令集架构"与"具体实现"分开，软件从此不必为每台机器重写。随后 Unix 用进程、虚拟内存、文件、权限，把一台裸机抽象成多个互不干扰的世界。

今天的 harness 在做同一件事：把模型抽象成可调度、可隔离、可审计的执行单元。

| 操作系统 | Agent Harness | 作用 |
|---|---|---|
| CPU | 模型权重 | 真正的算力，但不理解"任务" |
| 进程与调度器 | 主循环、子 Agent、步数/递归上限 | 把一次推理变成可中断、可并行的执行流 |
| 虚拟内存与页表 | 上下文窗口、压缩、检索、技能渐进披露 | 用小而快的"内存"假装拥有无限上下文 |
| 文件系统 | 工作区、记忆库、append-only 日志 | 让状态跨会话持久化 |
| 系统调用与权限位 | 工具调用、审批门、沙箱 | 把"能做什么"变成显式契约 |
| 中断与信号 | human-in-the-loop、hooks | 允许人随时接管 |
| 设备驱动 / ABI | MCP、A2A、AG-UI | 让工具与 Agent 即插即用 |
| dmesg / 审计日志 | 结构化 trace、回放、分叉 | 事后可解释、可复现 |

其中三处对应关系，值得展开。

### 3.1 上下文窗口就是物理内存

窗口大小是 RAM 容量，压缩是 swap，检索是 page fault，技能的渐进式披露是按需分页（demand paging）。DeepSeek Harness 的 PTC 模式更直白：让模型写一段代码去编排多轮工具调用，中间数据留在运行环境里，只有最终结果进入上下文——相当于把中间结果留在用户态，不污染内核页。

上下文不是越大越好。研究表明模型对长上下文中间部分的信息利用最弱（lost in the middle）；无关内容会稀释注意力；token 成本还随长度增长。更隐蔽的是**上下文抖动**：压缩太频繁，关键约束被摘要丢掉，Agent 开始反复读同一个文件、反复推翻同一个决定——和操作系统的 thrashing 一模一样。判断信号很朴素：同一份材料被读了三遍，说明你的"换页策略"坏了。

```text {linenos=false}
上下文窗口（物理内存）
├── 常驻：系统提示词 / 当前目标 / 最近一次失败输出
├── 可换出：历史轨迹 → 摘要（swap，有信息损失）
└── 按需调页：技能文档 / 代码检索 / 长期记忆（page fault）
```

所以 harness 的"上下文预算管理"，本质是一个内存调度器：什么常驻、什么换出、什么按需调页，三件事决定成本与稳定性。

### 3.2 沙箱不是安全围栏，是 MMU

普通操作在沙箱内自由执行，危险操作触发审批——这就是用户态与内核态：日常计算不打扰内核，只有系统调用才陷入。

但隔离的价值不止于安全。它同时是**认知边界**：工作区越干净，模型需要推理的状态空间越小，越不容易被无关文件带偏。这解释了一个反直觉的现象——给 Agent 一个干净的容器，往往比写一段更长的 prompt 更有效。你减少的不是风险，是它要理解的世界。

### 3.3 append-only 日志就是 WAL

DeepSeek Harness 有一个数据库味很重的设计：模型看到的一切——系统提示词、思维链、工具调用与结果、子 Agent 调度、每一次上下文注入——都写入仅追加（append-only）的会话日志；恢复、分叉、检索、回放共享同一份事件流。

这就是 WAL + checkpoint + redo：先写日志，再改状态；崩溃后重放；想试分支，就 fork 一份日志。它也是 event sourcing：状态是事件流的投影，而不是某个时刻的快照。

由此得到一条硬标准：**一个不能回放的 harness，不配谈生产可用。** 可审计性不来自模型的"自觉"，而来自日志的完备性。

## 四、三种外部化：记忆、技能、协议

上海交大等机构的综述（arXiv:2604.08224）给了一个统一视角：Agent 的进步，本质是**认知外部化**——把原本要求模型在参数里"回忆"的负担，转移到模型外部的显式结构中。

这是诺曼"认知制品"的老思想：购物清单不提升记忆力，它把"回忆还差什么"改造成"看一眼清单"。语言、文字、印刷、计算器，人类用几千年走完这条路；LLM Agent 把时间轴压缩到了几年。

| 外部化 | 搬走了什么负担 | 典型形态 | 主要代价 |
|---|---|---|---|
| 记忆 | 跨时间的状态 | 工作/情节/语义/个性化四层，写-管-读循环 | 检索错、记忆污染、遗忘策略 |
| 技能 | 程序性专长 | SKILL.md、AGENTS.md、渐进式披露 | 库膨胀、选择困难、技能腐烂 |
| 协议 | 交互结构 | MCP、A2A、ACP、AG-UI | 协议税、版本兼容 |
| Harness | 以上三者的协调 | 循环、沙箱、审批、预算、trace | 工程复杂度、过拟合锁定 |

**记忆**的关键洞察是：价值不在存了多少，而在能否把"从参数中回忆"变成"从结构中检索"。但记忆不是网盘，是 cache——检索错一次比没有记忆更糟，错误上下文比空上下文更有害。所以它需要 TTL、失效机制和来源标注。

**技能**把"每次从零发明流程"变成"加载、识别、适配已有流程"。Claude Code 的做法是渐进式披露：先只暴露技能名，任务需要时才加载全文，避免上下文过载。代价是技能库一大，"选哪个技能"本身变成新的检索问题；API 一变，技能就会腐烂。

**协议**把"靠模型猜格式和权限"变成"遵循显式契约"。MCP 是工具界的 ABI，A2A/ACP 是 Agent 间的 IPC，AG-UI 是显示协议。代价是协议税：工具描述本身要吃上下文，版本还要兼容。

## 五、真正的 trade-off：参数化 vs 外部化

外部化不是免费的。多一次检索，多一次延迟和一个失败点；多一个技能文件，多一份上下文开销；多一层协议，多一处兼容成本。它换来的是可修改、可审计、可回滚、可组合。

| 特征 | 内化进权重 | 外化为结构 |
|---|---|---|
| 高频、稳定、可形式化 | ✅ 工具调用、格式遵循 | |
| 长尾、易变、需审计 | | ✅ 业务规则、权限、流程 |
| 更新频率 | 低（重训） | 高（改文件） |
| 出错之后 | 难以解释 | 可回滚、可定位 |

这条边界会**双向移动**：模型变强，会把外部能力收回权重（tool use 正在原生化）；harness 变丰富，又会对模型提出新要求（遵守分阶段注入、响应结构化约束）。二者共同进化。

共同进化有副作用。模型在后训练时见惯了某种 harness 结构，一旦换掉工具逻辑，性能就会掉——模型过拟合了自己的挽具。这是一种比 API 锁定更隐蔽的锁定：你锁的不是接口，是模型的"肌肉记忆"。反过来说，最适合你任务的 harness，未必是模型被训练时用的那个，针对具体任务仍然有真实的优化空间。

## 六、给工程实践的五条清单

1. **评测要控制变量**：固定 harness 比模型，或固定模型比 harness。混在一起测，结论无效。
2. **让 context 比 harness 活得久**：记忆、决策记录、审计轨迹要做成可迁移资产；harness 只是可替换的外壳。
3. **五个旋钮先设好**：最大步数/递归深度、上下文预算、审批门、沙箱范围、结构化 trace。自主度是参数，不是开关。
4. **先抄收敛设计**：Codex 与 Claude Code 在循环控制、隔离、审批、可观测性上高度收敛。这不是巧合，是结构性需求。
5. **用"可回放"验收**：任何不能重放的事故，都等于没修好。

## 结语：智能分布在主体与环境之间

诺曼说过，智能不存在于孤立的主体之内，而分布在主体与其认知环境之间。对人类，这个环境是语言、文字、制度与工具；对 Agent，是记忆、技能、协议，以及把它们协调起来的 harness。

所以"Agent 工程"并不是一个凭空出现的新学科。它是操作系统与软件工程的老手艺——抽象、接口、隔离、日志、权限——换了一个载体重新长出来。模型会继续变强，今天外置的很多东西明天会被吸回权重；但"如何组织认知"这个问题不会消失，它只会换一层皮。

模型决定上限，harness 决定你能不能稳定地摸到那个上限。
