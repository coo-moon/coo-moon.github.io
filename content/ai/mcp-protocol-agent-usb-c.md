# MCP 协议：Agent 的“USB-C”是怎么炼成的？

> 2026 年 7 月 28 日，MCP（Model Context Protocol）发布了自 2024 年 11 月开源以来最大的一次更新：正式废弃 `initialize` 握手，协议层彻底无状态化。此时距它成为“AI 界的事实标准”不过一年多——公共 Server 超过 1 万个、Python/TypeScript SDK 月下载量 9700 万+。它凭什么统一了 Agent 生态？这背后是一套怎样的协议内核？

---

## 一、先讲人话：从“一机一充”到万能插座

想象 2010 年的抽屉：诺基亚、摩托罗拉、索爱，每台手机一个充电头，出门带三根线。后来 USB-C 一统江湖——一根线，所有设备通吃。

2024 年以前的 AI 世界就是“一机一充”：每个模型有私有的 function calling 格式，每个工具要单独写适配器。接 10 个模型 × 10 个工具，就要维护 100 条“专用充电线”——业界称之为 **M×N 集成问题**。MCP 就是那根 USB-C 线：**模型端实现一次客户端，工具端实现一次服务器，双方说同一种“语言”，集成成本从 N×M 降到 N+M**。

## 二、协议内核：三个角色、两种传输、四大原语

MCP 的架构只有三个角色：

```
┌──────────────── Host（宿主应用）────────────────┐
│   Claude Desktop / VS Code / Cursor / ChatGPT    │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐      │
│   │ MCP Client│  │ MCP Client│  │ MCP Client│    │  ← 1:1 专线连接
│   └────┬─────┘  └────┬─────┘  └────┬─────┘      │
└────────┼─────────────┼─────────────┼────────────┘
         ▼             ▼             ▼
    ┌─────────┐   ┌─────────┐   ┌─────────┐
    │ MCP Server│  │ MCP Server│  │ MCP Server│
    │  GitHub  │   │  数据库   │   │  浏览器  │
    └─────────┘   └─────────┘   └─────────┘
```

- **Host（宿主）**：面向用户的 AI 应用，持有模型和会话，负责决策“调哪个工具”；
- **Client（客户端）**：Host 内部与某个 Server 一一对应的连接组件，负责翻译和转发消息；
- **Server（服务器）**：暴露能力的“接线板”，把数据库、GitHub、浏览器包装成标准接口。

**消息格式**采用 JSON-RPC 2.0——一种比 REST 更轻量的远程调用协议，只有三种消息：请求（Request）、响应（Response）和无需回复的通知（Notification）。

**四大原语**（Server 能暴露什么）：

| 原语 | 作用 | 一句话类比 |
|---|---|---|
| Tools 工具 | 可执行的函数（JSON Schema 校验参数） | 让 AI 动手“做事”：查天气、发邮件 |
| Resources 资源 | 可读取的数据（URI 寻址） | 让 AI 查阅“资料”：读文件、看文档 |
| Prompts 提示词 | 可复用的提示模板 | 给 AI 递“话术卡”：固定格式指令 |
| Sampling 采样 | 反向请求：Server 请 Client 调一次 LLM | 工具反过来“借用”模型的脑子 |

**传输层**两条路：本地用 **stdio**（标准输入输出，零网络开销，IDE 插件就是这么跑的）；远程用 **Streamable HTTP**（一个 POST 端点搞定，适合云端服务）。

## 三、一次真实调用长什么样

以“让 AI 查 GitHub 上最火的 MCP 仓库”为例。客户端先 `tools/list` 问 Server 有什么工具：

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/list"}
```

拿到工具清单后发起调用：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "search_repos",
    "arguments": {"query": "MCP", "sort": "stars"}
  }
}
```

Server 执行完把结果返回，Host 将结果拼进上下文交给大模型，模型据此生成最终回答。整个过程**模型不直接碰工具，工具也不直接碰模型**——中间隔着一个标准协议。这正是“解耦”的威力：换模型不用改工具，换工具不用改模型。

## 四、本月最热的内核新闻：2026-07-28 无状态化革命

7 月 28 日发布的新规范是 MCP 史上最大的一次破坏性更新，核心就一句话：**协议层彻底无状态化**。

**以前为什么要有状态？** 旧版 MCP 要求连接时先走 `initialize` 握手：客户端报上“我是谁、支持哪个协议版本、有什么能力”，服务器回赠自己的能力清单；之后所有请求都携带 `Mcp-Session-Id` 会话头，服务端必须记住“这个会话的对方是谁、能干什么”。

**现在改成了什么？** 握手和会话头一并废除（SEP-2575 / SEP-2567），每个请求自报家门：协议版本、客户端身份、能力清单全部放进 `_meta` 字段随请求携带；想知道服务器能力？随时调新的 `server/discover` RPC 现查。用官方博客的话说：**任意请求可以落在任意一台服务器上**。

**为什么要这么改？** 企业规模化倒逼的。有状态会话意味着：请求必须被“粘性路由”到同一台机器、网关无法随意转发、Server 难以水平伸缩、冷启动还得先握手。而无状态让 MCP Server 变成纯 REST 式服务——**负载均衡随便转发、K8s 随便扩缩容、Serverless 随用随起**。配套地，Streamable HTTP 传输现在要求请求头带 `Mcp-Method` 和 `Mcp-Name`，让网关和限流器不用解析 body 就能按“操作类型”路由——和 HTTP 方法之于 Web 网关是同一个道理。

**代价是什么？** 每次请求都要重复携带身份与能力信息（消息变大、协商成本前置）；Server 无法隐式记住跨请求状态，需要状态就得自己外置存储。这是分布式系统最经典的 trade-off：**用会话便利性换可伸缩性**——与 HTTP 从长连接到无状态 API 的演进如出一辙。

## 五、MCP ≠ 一切：三层协议栈

MCP 解决的是“AI 与工具”的连接。但 Agent 之间怎么对话？网页怎么访问？2025 年 4 月 Google 发布 A2A（Agent-to-Agent）协议，IBM 的 ACP 于 2025 年 8 月并入；2025 年 12 月，Linux 基金会成立 Agentic AI Foundation（AAIF），OpenAI、Google、微软、AWS 等齐聚一堂，Anthropic 把 MCP 捐赠给该基金会，A2A 也同步入驻。业界正在形成共识的三层协议栈：

| 层级 | 协议 | 解决什么 | 一句话 |
|---|---|---|---|
| 工具层 | MCP | AI ↔ 工具/数据 | 给 AI 装“手” |
| 智能体层 | A2A | Agent ↔ Agent | 让 AI 组“队” |
| 网页层 | WebMCP | AI ↔ 万维网 | 给 AI 装“眼” |

## 六、冷静一下：工具即权限

协议越通用，安全边界越重要。MCP 的每个工具都是一次“授权执行”——**工具即权限**。当前最受关注的风险是提示注入（prompt injection）：恶意网页或文档内容可能诱导模型调用敏感工具。实践中需要组合拳：最小权限原则（只暴露必要工具）、工具参数白名单校验、敏感操作人工确认、对工具输出标注“不可信来源”。协议解决的是“能不能连得上”，安全还得靠“该不该连”的治理。

## 七、回望与展望

回看 MCP 的两年：2024 年 11 月 Anthropic 开源（起因是工程师在 IDE 和 Claude Desktop 之间反复复制代码的“偷懒”）；2025 年 3 月 OpenAI 宣布全系接入，成为行业拐点；2025 年 12 月捐赠给 AAIF，从“一家公司的标准”变成“行业公共品”；2026 年 7 月无状态化，从“能用”走向“企业级规模化”。

这条路径和 USB、SQL、HTTP 何其相似——**技术标准化的规律从未变过：先解决一个具体痛点，再靠生态滚雪球，最后由中立机构接管治理**。对开发者来说，现在学 MCP 就像 2010 年学 USB-C：方向已经写死在历史里了。
