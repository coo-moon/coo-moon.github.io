# 向量索引的软肋是"写入"：拆解 LSM-VEC，当 LSM 树遇上 HNSW 图

> 2026 年 9 月 4 日，VLDB 2026 的 VecDB 向量数据库研讨会在波士顿开场。这个从去年起就场场爆满的会场，热度背后是行业撞上的同一堵墙：**RAG 的知识库天天在变，而主流的向量索引天生"怕写"**。墙那边，一篇 2025 年 5 月挂上 arXiv 的论文 LSM-VEC 给出了一个"用数据库内核老办法解向量新难题"的思路：把 LSM 树直接焊进 HNSW 图。它为什么值得关注？得先看清 HNSW 的"写"到底有多痛。

## 一、先讲人话：一张"只建不修"的地铁图

把上一篇文章里的 HNSW 想象成一张贴在墙上的地铁图：

- **加一个新站**：要在图上重新画线、把新站连进现有线路——连哪几条线、和谁换乘，都要现算；
- **拆一个旧站**：不能把墙纸撕了重画，只能贴一张"本站停运"的条子。站还在图上，路过的车还得绕开它；
- **城市一直盖楼**：几年下来，墙上贴满停运条子，线路绕来绕去，这张图越来越难用——只能整张撕掉重画。

HNSW 的"加站"叫插入，那张"停运条子"叫**墓碑（tombstone）**，"整张撕掉重画"叫**索引重建**。数据库内核这边早就有一套完全不同的哲学——**LSM 树**：像餐厅后厨，客人点单先随手贴墙上（内存缓冲），积攒到一定量再统一誊写进菜单本（顺序落盘），菜单本太乱时后半夜慢慢整理合并（compaction）。**先随便记，后统一理**——这就是 LSM 对"写"的全部回答。

## 二、HNSW 的"写"有多痛

HNSW 是读优化的艺术品，写起来处处是坑：

| 操作 | 代价 | 后果 |
|------|------|------|
| **插入** | 新节点连边只看"此刻已有的点"，不回看历史 | 长期写入后**图漂移**：图结构渐渐偏离最优 |
| **删除** | 墓碑标记，物理不删 | 死边残留、查询绕路，图"慢慢腐烂" |
| **更新** | = 删除 + 插入，两份代价 | 高频场景写放大显著 |
| **重建** | 删除比例超过 10%~20%（社区经验值）就得重建 | Qdrant `optimize`、Milvus compaction 都是干这个的 |
| **内存** | 1536 维、M=16 时单向量约 6.3KB | 一千万条 ≈ 63GB，全内存图的宿命 |

还有两个工程细节：图索引的**写入是单线程瓶颈**，Qdrant、Milvus 都用"分段构建"来绕；而电商目录这种高频更新场景，SIGIR eCom 2026 的论文专门研究了累计更新下如何把召回衰减控制在 1%~3%——注意，是"研究如何控制"，不是"天然没问题"。

一句话：**检索有多爽，写入就有多痛。** 静态数据集时代这无所谓，但 2026 年的 RAG 应用——新闻抓取、聊天记录沉淀、商品目录——全是持续写入的活数据。

## 三、数据库内核的"老答案"：LSM 树速成

LSM（Log-Structured Merge Tree）不是新东西：1996 年 O'Neil 等人提出，2006 年被 Bigtable 论文发扬光大，2011 年 Jeff Dean 和 Sanjay Ghemawat 做出 LevelDB，2013 年 Facebook 移植为 RocksDB，成为 Cassandra、TiKV、MyRocks 的底座。核心结构就三样：

```
写入 ──► WAL(顺序日志) ──► Memtable(内存跳表) ─┐
                                              │ 满了
                                              ▼
                SSTable 0 ◄── 落盘(顺序写) ──┘
                SSTable 1 ◄── compaction(后台合并整理)
                SSTable 2 ◄── ...
```

哲学就一句话：**把随机写变成顺序写，用后台批量整理换前台高吞吐**。代价是经典三兄弟：

- **写放大**：一条数据被 compaction 反复搬运；
- **读放大**：要查多层 SSTable，靠 **Bloom filter** 快速跳过无关文件；
- **空间放大**：旧数据等着被合并回收，磁盘占用暂时虚高。

leveled（分层合并）和 tiered（分代合并）两种策略，就是在三个放大之间调旋钮。这套"写友好"设计，就是 LSM-VEC 的弹药库。

## 四、LSM-VEC：把 HNSW 的"主图"搬进 LSM

LSM-VEC（arXiv:2505.17152）的逻辑非常直接：既然 HNSW 的痛点都是**图要动**，那就让最擅长处理"大量小写入"的 LSM 来管图。架构分两层：

```
   内存        ┌────────────────────────────┐
              │  HNSW 上层小图(查询入口/热数据) │
             ┌┴────────────────────────────┴┐
             │  HNSW 底层大图(major layer)    │
   磁盘       │  由「图优化的 LSM 树」(AsterDB) │
             │  维护：插入/删除 = LSM 写+后台合并 │
             └─────────────────────────────┘
```

- **主图（major layer）落盘**，用图优化的 LSM 树（AsterDB，Mo et al., 2025）维护——每次插入/删除都会在图里掀起大量边更新，这正是 LSM"攒起来后台合并"的舒适区，**不需要全局重构**；
- **小图（upper layers）留内存**，承担查询入口和热数据，保住毫秒级入口延迟；
- **局部性重排**（locality-aware reordering）：让图的磁盘布局贴合访问模式，把随机 I/O 压成顺序 I/O——和 LSM 的落盘思路一脉相承；
- **采样式维护**（sampling-based maintenance）：修图不全量重连，只对局部邻居抽样更新，控制写放大。

实验结果（SIFT1B 十亿级数据集）：在**召回、延迟、更新效率、内存占用**四个维度上全面优于 DiskANN 和 SPFresh 两个磁盘型基线，论文自称是首个把 LSM 树用于支撑向量索引高效增删的系统。

当然没有银弹：图 LSM 的**粗粒度分区会损伤召回**（这也是 AsterDB 路线被质疑的点），compaction 期间查询延迟也可能抖动——LSM 的旧债，换了赛道照样要还。

## 五、这不是孤例：全行业都在偷偷"LSM 化"

LSM-VEC 的新颖之处是把 LSM 写进了"索引内核"，但它不是唯一闻到这个味道的：

- **FreshDiskANN**：RW-Store（内存可写图，支持增删）+ RO-Store（磁盘只读图），StreamingMerge 后台把前者合并进后者——明摆着的 memtable + compaction，作者自己都承认设计哲学与 LSM 高度一致；
- **GaussDB-Vector**（VLDB 2025）：十亿级实时更新，搜索 5000 QPS、更新 3000 QPS，删除后还专门把"失联节点"重新插回图里修路；
- **Milvus**：分段存储 + DeltaLog 记录删除 + compaction 合并——存储层本来就是 LSM 同构的思想；
- **Qdrant**：optimize 触发图的局部重连和整理。

工业界早已在用 LSM 思想打补丁，LSM-VEC 干的只是把这层窗户纸捅破：**把"索引"本身当成 LSM 来管**。

## 六、权衡与选型：你的场景该信谁

| 场景 | 推荐 | 理由 |
|------|------|------|
| 文档快照型 RAG（建库后几乎不变） | 内存 HNSW（Milvus/Qdrant/pgvector） | 检索性能拉满，写入短板无所谓 |
| 持续摄入 + 千万~亿级 | 磁盘图 + LSM 化更新（DiskANN/FreshDiskANN 路线） | 写友好、内存可控，牺牲一点延迟 |
| 高频删改 + 亿级实时 | LSM-VEC 这类"LSM 管图"方案（研究→工程化中） | 更新不触发全局重构 |
| 百万级 + 想复用 SQL 生态 | pgvector HNSW | 省一套基建；删多了记得定时 rebuild |

## 七、总结：每一种索引都要过"写入"这一关

回看数据库五十年：B+树统治读密集场景，LSM 因写密集场景而生，两者的交锋最终以"按 workload 分治"收场。今天的向量检索正完整重演这段历史：先是内存图索引称王（HNSW），接着是磁盘化浪潮（DiskANN），现在轮到"动态更新"这个终局难题——而答案居然是从 1996 年的论文里借来的。

这给所有搞 AI 基建的人一个朴素但扎心的启示：**索引的本质是"给数据找路"，而路会旧、会堵，能随数据一起生长的路才是好路。** 下次你的 RAG 知识库一天更新几千条新闻，别再条件反射地"全量重建索引"了——先想想 LSM 教给我们的三句话：随机写改顺序写、小写攒成大批、后台慢慢整理。向量数据库的下一个十年，可能就藏在这三句话里。
