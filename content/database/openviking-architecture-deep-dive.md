> 上一篇[《Hermes Agent 接入 OpenViking 实战》](/posts/hermes-openviking-setup/)记录了接入过程。这篇往下挖一层：它的**数据模型为什么这么设计**、检索算法怎么工作、以及作为"数据库"它做对了哪些事。

## 一、先回答一个根本问题：为什么需要"上下文数据库"

传统 RAG 管道的典型形态：文档切块 → 嵌入 → 扔进向量库 → 检索时取 top-k。这个范式有三个结构性问题：

1. **块是孤岛**——chunk 检索回来时丢失了它在原文档中的位置和上下文
2. **黑盒检索**——结果不对时，你无法知道"为什么返回了这几块"
3. **无状态**——Agent 的记忆、知识、技能各存一处，没有统一操作界面

OpenViking 的答案是把这些全部**文件系统化**：

```
viking://
├── resources/          # 资源：项目文档、代码仓库、网页
├── user/{user_id}/
│   ├── memories/       # 长期记忆（自动提取）
│   ├── skills/         # 技能
│   └── sessions/       # 会话归档
```

Agent 操作上下文就像开发者操作文件——`ls`、`tree`、`find`、`grep`，每个对象有稳定 URI。这不是怀旧式的拟物，而是利用了文件系统两个被验证几十年的性质：**层级聚合语义**（目录天然表达"这堆东西是一类"）和**路径可解释性**（任何结果的来源是一条可追溯的路径）。

## 二、三层信息模型（L0/L1/L2）

这是整个系统最核心的设计。写入时，每个**目录**会被生成两层语义摘要：

| 层 | 文件 | 默认上限 | 用途 |
|---|---|---|---|
| **L0 Abstract** | `.abstract.md` | 256 字符 | 向量检索、快速相关性判断 |
| **L1 Overview** | `.overview.md` | 4000 字符 | Rerank、导航、"要不要读全文"的决策 |
| **L2 Detail** | 原始文件 | 无限制 | 全文，按需加载 |

```
viking://resources/docs/auth/
├── .abstract.md     # L0："API 认证指南，覆盖 OAuth2/JWT/API Key"
├── .overview.md     # L1：结构化概览 + 快速导航（oauth.md 讲什么、jwt.md 讲什么）
├── oauth.md         # L2：全文
└── jwt.md           # L2：全文
```

几个值得注意的设计细节：

**摘要是目录级而非文件级的**。普通文件不单独建 L0/L1 sidecar，文件摘要作为素材聚合成所属目录的 L1。这个选择很聪明——如果每个文件都有摘要，一个万文件仓库就是两万个 sidecar，维护成本爆炸；而目录级摘要天然控制了元数据规模，且与人类组织知识的习惯一致。

**L0 是从 L1 里抽出来的**（H1 标题后、第一个 `##` 之前的段落），不是独立生成的。保证了两层摘要的一致性，省一次 LLM 调用。

**生成是异步、自底向上的**。文档进入后走 `SemanticQueue` 异步处理，先有文件级摘要再聚合出目录级。所以刚挂载的资源要等一会儿才能搜到——上一篇文章里我们实测过这个延迟。

**成本结构变了**。传统 RAG 每次查询都要把 top-k chunk 全文塞给 LLM；这套模型下，Agent 先花 ~100 token 看 L0 判断相关性，再花 ~2k token 读 L1 决定路线，最后才按需加载 L2。官方 benchmark 里输入 token 降 34%-91%，主要就省在这里。

## 三、双层存储：内容与索引分离

```
        VikingFS (URI 抽象层)
        ┌──────┴──────┐
  Vector Index      AGFS (RAGFS)
  只存 URI+向量+元数据   存全部内容
```

**AGFS 存内容**（已用 Rust 重写为 RAGFS），支持 localfs / S3 / memory 多后端，多写模式可以做副本和迁移；**向量索引只存引用**——URI、向量、元数据，不含任何文件内容。

这是数据库领域经典的"索引与数据分离"，好处也一模一样：

1. **单一数据源**——所有读取走 AGFS，索引只是加速器，重建索引不丢数据
2. **内存友好**——向量服务不背内容，同样的内存能装大得多的索引
3. **独立扩展**——内容层和索引层可以分开扩容

## 四、检索算法：目录递归 + 分数传播

这是最有"数据库味"的部分。查询分两条路：

### find() vs search()

| | find() | search() |
|---|---|---|
| 意图分析 | 不做 | LLM 分析出 0~5 个 TypedQuery |
| 会话上下文 | 不需要 | 必须 |
| 延迟 | 低 | 高 |
| 适用 | 简单查询 | 复杂任务 |

search() 的意图分析会把一个问题改写成多个带类型的子查询——`skill` 型（动词开头）、`resource` 型（名词短语）、`memory` 型（"用户的 XX"），各自路由到不同的根目录（memories/resources/skills），闲聊甚至会被判定为 0 查询直接跳过检索。

### 层级递归检索

核心思想：**先全局定位起点目录，再沿目录树向下钻**。

```
Step 1  按 context_type 定位根目录
Step 2  全局向量搜索，找到得分最高的起始目录
Step 3  合并起点 + Rerank 打分
Step 4  优先队列驱动的递归搜索：
        final_score = α·embedding_score + (1-α)·parent_score
Step 5  连续 3 轮 topk 无变化 → 收敛退出
```

关键在**分数传播公式**：子节点的最终分数由自身嵌入分和父目录分加权而来。这意味着一个嵌入分平平但身处高分目录下的文件，依然有机会被召回——这正是解决"chunk 孤岛"问题的机制，检索结果天然带着它的上下文位置。

整个过程留下完整的**浏览轨迹**（trajectory），结果可疑时可以回放"它先进了哪个目录、在哪一层放弃了"。传统向量库的黑盒检索在这变成了可调试的白盒。

## 五、会话即记忆：Schema 驱动的记忆提取

Session 生命周期是 `Create → Interact → Commit`。commit 时同步归档对话，然后异步跑两件事：

1. **压缩去重**——Compressor 对历史做摘要合并
2. **记忆提取**——按 Schema 抽取结构化记忆，LLM 决定与已有记忆是合并还是新增

提取出的记忆落入 `viking://user/{user_id}/memories/` 下的分类目录（偏好/实体/事件等），之后参与正常的语义检索。也就是说，**记忆的写入路径和知识的写入路径是同一条**——都是资源，都进同一套分层索引，没有为记忆单造一套子系统。

学术侧这套设计有论文支撑：*VikingMem: A Memory Base Management System for Stateful LLM-based Applications*（VLDB 2026），开源版是其核心能力的子集。

## 六、我的评价

用了几天之后，我认为它做对的三个决策：

1. **URI 作为一等公民**。所有能力（检索、权限、引用、溯源）都挂在稳定路径上，这让"上下文管理"第一次有了可以脚本化的接口。
2. **把 LLM 放在正确的位置**。LLM 只出现在摘要生成、意图分析、记忆提取这些离线/低频环节；检索主路径是纯向量计算 + 优先队列，延迟可控。
3. **诚实的工程取舍**。比如"L0 从 L1 抽取而非独立生成"、"摘要只建目录级"，都是在规模和质量之间选了可持续的那端。

值得观望的点：目录级摘要意味着粒度受限于目录划分的好坏，挂载时怎么组织目录结构会成为新的"建模"工作；另外语义处理依赖外部 VLM/embedding 服务，本地全离线场景要多斟酌模型配置。

对于在做 AI Agent 基础设施的人来说，这个项目值得精读源码——它可能是目前最完整的"把数据库方法论应用于上下文工程"的开源实现。
