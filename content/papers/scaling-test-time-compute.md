# Scaling LLM Test-Time Compute Optimally — 论文精读

> **原文**：[arXiv:2408.03314](https://arxiv.org/abs/2408.03314)，2024 年 8 月 6 日
> **作者**：Charlie Snell（UC Berkeley）、Jaehoon Lee、Kelvin Xu、Aviral Kumar（Google DeepMind）
> **一句话**：如果让模型在**答题时**多花算力，怎么花才最划算？答案是：按题目难度自适应分配，效率比 best-of-N 高 4 倍；在匹配 FLOPs 的对比下，小模型 + 想更久可以打败 14 倍大的模型。

这篇论文发表的时间点很有意思：2024 年 8 月，OpenAI o1 发布前一个月。它没有训练任何"推理模型"，却系统回答了推理模型为什么有效、怎么用才高效——后来 o1/R1 掀起的 test-time scaling 浪潮，本质上是在验证这篇论文的预言。我此前写过一篇综述[《AI 开始"打草稿"了》](/posts/reasoning-models-test-time-compute/)讲行业图景，这一篇是论文本体的逐节拆解。

---

## 一、论文要回答的问题

人类在难题上会想得更久。那么：

> **如果一个 LLM 被允许使用一笔固定的、不可忽视的推理时计算（inference-time compute），它在一道难题上到底能提升多少？**

这个问题不只在学术上有趣，它直接决定两件事：

1. **部署经济学**：如果"小模型多想一会儿"能追平"大模型直接答"，那端侧小模型 + 充足推理算力，可能替代数据中心级大模型。
2. **预训练的方向**：未来的算力预算，应该继续堆在 pretraining，还是挪一部分到 inference？

论文之前的文献给的是**互相矛盾的答案**：有的工作说测试时计算有效（self-consistency、best-of-N、PRM），有的说在数学推理这类复杂任务上基本没用。作者认为缺的不是新方法，而是一个**系统性分析**——不同方法在不同条件下各自的 scaling 行为是什么样。

## 二、统一框架：Proposer + Verifier

论文把当时所有测试时增强方法抽象成两个组件：

```
提议者 π(y|x)          验证器 V(y, x)
"模型给出答案分布"       "给答案打分"
────────────────       ────────────────
best-of-N        →     采样 N 个答案，选分最高的
PRM 树搜索       →     逐步打分 + 搜索
迭代修订         →     修改提议分布本身（模型自己改自己的答案）
majority voting  →     用一个"永远给满分"的验证器
```

于是"怎么花测试时算力"就拆成两条正交的轴：

- **轴一：优化验证器（搜索）**——怎么在验证器上更聪明地搜索。best-of-N 是"粗搜索"，过程奖励模型（PRM）+ 树搜索是"细搜索"。
- **轴二：改造提议分布（修订）**——让模型在拿到初始答案后，**序列地**迭代改进自己的答案，而不是只并行采样互不相干的 N 份。

这两条轴对应的就是文章标题里的 "scaling test-time compute" 的两种主要机制。

## 三、实验设定：一个容易被忽略的关键设计

- **数据集**：MATH（高中竞赛数学，12k 训练 / 500 测试），选它是因为测试时计算最适合"知识已具备、难在推理链条"的任务。
- **基座模型**：PaLM 2-S*（Codey 变体），在 MATH 上有非平凡的通过率但远未饱和——正好当试验田。
- **能力要靠微调注入**：即便是当时最强的闭源模型，直接 prompt 它"检查并修改自己的答案"也几乎无效。所以 PRM 和修订模型（revision model）都是专门微调出来的。这一点在 2024 年是硬约束，在 2026 年已经基本被预训练原生解决（R1 之后的模型天生会反思）。

### 难度怎么定义？

这是全文最重要的自变量。作者**不用** MATH 数据集自带的人工难度标签，而是从**模型视角**定义：

> 对每道测试题，让基座模型采样 2048 次，估计 pass@1，然后按 pass@1 分位数把题目分成 **5 个难度档（bin 1 最简单 → bin 5 最难）**。

实践里还要解决"上线时没有标准答案"的问题：真值 pass@1 是 oracle 难度，部署时改用 **PRM 打分的预测难度**（同样 2048 次采样，但用验证器分数代替正确性判断）。实验证明两者几乎给出同样的分箱——这让"难度自适应"在真实系统里可落地。

## 四、发现一：搜索类方法——beam search 不是免费的午餐

作者对比了三种在 PRM 上搜索的策略（生成预算用"等效采样次数"归一，比如 4/16/64/256）：

| 方法 | 做法 | 特点 |
|---|---|---|
| Best-of-N | 并行采 N 个完整答案，按 PRM 终分选最优 | 简单，无过度优化风险 |
| Beam Search | 每步扩展 N 个候选，PRM 保留 top-M 继续 | 对 PRM 打分做逐步优化 |
| Lookahead Search | beam search 的每步评估再多看 k 步 rollout | 最强（最贵）的逐步优化，近似去随机化的 MCTS |

结果非常反直觉：

1. **低预算时 beam search 明显优于 best-of-N；但预算拉大后优势消失，甚至反超为不及 best-of-N**。lookahead search 全程最差。
2. **原因是"过度优化验证器"**：搜索是在榨 PRM 分数的每一分好处，预算越大越能找到 PRM 的漏洞——论文附录里抓到过搜索结果生成的"无信息重复步骤"和只有一两步的超短答案。更强的优化器（lookahead）死得更快。
3. **按难度分箱后规律浮现**：简单题（bin 1-2）上 beam search 随预算**性能退化**（验证器本来就判断得对，继续优化只会放大它的伪特征）；中等题（bin 3-4）beam search 稳定优于 best-of-N（模型自己采不出正确答案，搜索的引导有价值）；**最难档（bin 5）所有方法都没有实质进步**。

> Takeaway：不存在普适最优的搜索算法。beam search 适合"难题 + 低预算"，best-of-N 适合"易题 + 高预算"。

## 五、发现二：修订类方法——序列思考 vs 并行采样

第二条轴是把算力花在**改造提议分布**上：微调一个修订模型，输入"题目 + 之前最多 4 个错误答案"，输出改进后的答案。训练数据构造很巧：并行采 64 个答案，把正确答案和若干**编辑距离相近**的错误答案配成多轮修订轨迹做 SFT。

三个关键结果：

1. **修订链真的有效**：revision 每一步 pass@1 缓慢爬升，而且**能泛化到超过训练长度的链**（训练只见过 4 步，推理时拉到 64 步仍在涨）。
2. **同样的预算，序列修订略优于并行采样**（配合验证器或多数投票选最终答案）。但有个坑：直接"拿着上一个答案继续改"会把约 **38% 的正确答案改错**（分布偏移：训练时上下文里全是错的，测试时混进对的）。解决办法是不取链尾，而是用验证器/投票在整条链里**选**最好的那个。
3. **最优的是混合配比**：并行采样像全局搜索（覆盖不同的高层解法），序列修订像局部精调（把接近对的答案改对）。扫描"序列 : 并行"的预算配比，每个总预算下都存在一个最优比例——**简单题全序列最好，难题需要保留一部分并行探索**。

> Takeaway：序列/并行之比也是一个需要按难度自适应的超参数。这一节其实就是后来 o1/R1 "既会反思又会在脑子里换思路"的雏形分析。

## 六、合起来：Compute-Optimal Scaling，效率提升 4 倍

把两条轴的发现形式化，就是论文的核心概念——**测试时计算最优策略**：

```
给定题目 x 和算力预算 C：
  π*(x, C) = argmax_θ  Acc( π_θ(y|x) )
  即：为每个难度档，在验证集上选出该预算下准确率最高的策略 θ
```

在测试集上用二折交叉验证评估。结果：

- **搜索场景**：按难度选策略，约等于 best-of-N 的表现，只花 **1/4 的算力**（如 16 次 vs 64 次生成）。
- **修订场景**：差距更大，**4 倍于 best-of-N 的算力效率**（64 vs 256）。
- 用"预测难度"替代"oracle 难度"曲线基本不衰减——方法可部署。

## 七、最炸裂也最常被误读的一节：能否替代预训练？

最后的 FLOPs-matched 实验回答"算力汇率"问题：

- 换算方式：预训练 FLOPs ≈ `6·N·D`（N 参数、D tokens），推理 FLOPs ≈ `2·N·T`（T 为生成 token 数）。把参数放大 14 倍，预训练和推理成本同步放大 14 倍；小模型要**追平总 FLOPs**，就得把推理算力乘的倍数取决于推理负载与预训练之比 `R = T/D`（论文试了 R = 0.16 / 0.79 / 22 三档）。
- 结论按难度分裂：
  - **易题、中等题**，或**推理负载低**的场景（如自我改进管线，生成量 ≪ 预训练量）：小模型 + compute-optimal 测试时算力 **打赢 14 倍大的模型**。
  - **最难题**，或**推理负载高**（R 很大，例如大规模线上服务）：还是把这些 FLOPs 花在预训练上更值。
  - 一句话：**测试时算力和预训练算力不是 1:1 可兑换的**。测试时计算是"能力区间内的放大器"，不是"能力的替代品"——模型根本不会做的题，想多久都没用（bin 5 全线无效）。

论文由此给出那个著名的展望：长期看，会更少的 FLOPs 花在预训练、更多的花在推理——这正是 2024-2026 年行业实际走过的路（o1→o3、R1→R1 蒸馏家族、各家 thinking budget 滑杆）。

## 八、局限与后续（截至 2026 年回看）

论文自己承认的：

- 难度估计本身要先花 2048 次采样，这部分成本没计入——**"多快判断该想多久"**是遗留的开放问题（exploration-exploitation）；
- 没试 PRM 搜索 × 修订的**组合**，也没试 critique-and-revise；
- 只在 MATH 一个域上做的分析。

站在 2026 年回看，哪些被后续证实、哪些被绕过了：

| 论文的判断 | 后续发展 |
|---|---|
| 测试时算力是第二条 scaling 曲线 | ✅ 已成行业共识，o3 在高算力档刷新 ARC-AGI，R1 用 RL 把"修订"内化进训练 |
| 简单题别过度搜索，会 reward hacking | ✅ 验证器过优化被反复复现；PRM 训练的 RL 现在普遍加防 hack 设计 |
| 难题上测试时算力收益很小 | ⚠️ 部分推翻——RL 训出的长思维链（而非外部搜索）在难题上确实能挖出增量，但"接近能力边界"仍是前提 |
| 难度自适应分配算力 | ✅ 变成产品形态：thinking budget 滑杆、Claude 的 adaptive thinking、路由式按需思考 |
| 把测试时成果蒸馏回基座 | ✅ 正是 R1 蒸馏、以及各家"推理数据回流预训练"的做法 |

## 九、核心公式与数字速查

| 项目 | 值 |
|---|---|
| 难度定义 | 基座模型 pass@1（2048 样本估计），5 个分位档 |
| 生成预算扫描 | 4 / 16 / 64 / 256 等效采样 |
| compute-optimal 效率增益 | ~4× less compute（搜索 16 vs 64；修订 64 vs 256） |
| 修订会把正确答案改错的比例 | ~38%（需验证器/投票兜底） |
| FLOPs 换算 | `C_pre ≈ 6ND`，`C_inf ≈ 2NT`，追平 14× 参数放大 |
| 结论的边界条件 | 易/中等题 + 低推理负载 → 测试时算力胜；难题或高负载 → 预训练胜 |
